# P1 — Cross-Lens Contradiction Readiness Assessment

**Build marker:** `cross-lens-readiness-audit-v1`
**Date:** 2026-02
**Mode:** READ-ONLY forensic audit. No code, prompts, calculators, flags, or chart docs modified.
**Companion:** `/app/backend/audit_reports/CROSS_LENS_CONTRADICTION_READINESS.json`

---

## TL;DR — Recommendation: **OPTION C — REQUIRES REDESIGN**

The flag is mis-named, the surface is mis-scoped, the engine is mis-personalized, and the recall is too poor for a user-facing surface. Concrete reasons:

1. **The flag does not surface "cross-lens" contradictions at all.** `CROSS_LENS_PROMPT_SURFACE` reads from `cross_lens_synthesis_v2.contradictions`, which is computed entirely from **intent-domain weights** (career/relationship/money/health/leadership/…) generated by a keyword classifier on the user's message. It does **not** compare Astrology vs HD vs Enneagram vs Numerology vs LoC. The `lens_coverage` field on the receipt is decorative — a regex scan of the user's message for words like "saturn" or "manifestor". No lens engine output participates in the contradiction decision.
2. **The lens-aware tension engine that DOES read per-lens signals (`services/tension_engine.py`) is largely hardcoded.** Every Manifestor receives the same `push_vs_hold` tension; every Enneagram 5 receives the same `logic_vs_instinct` tension; every Type-1 receives the same `control_vs_flow`. The astrology branch reads from a non-existent collection (`db.astrology_charts`) — the canonical collection is `db.charts` — so the astrology signal almost always falls back to a generic "energy in motion" / "momentum building" template. Result: the system that LOOKS like cross-lens synthesis is actually shipping pre-canned per-type strings.
3. **Recall is too low to be useful and precision too inconsistent to be safe.** On a 25-message replay (10 messages with genuine multi-domain tension, 10 single-domain / generic, 5 borderline) the v2 contradiction layer fired **5 total emissions**: 3 true positives, 1 same-thing-different-words (user stated the tension verbatim and the engine echoed it), 1 false positive on a benign chart question ("Tell me about my Saturn return" → "life_direction dominates over identity, delta 2.35"). Of 10 genuinely tension-bearing messages, only 4 produced any signal — recall ≈ 40%.
4. **The surfaced line is a category label, not a reflection.** When the flag is ON, the LLM receives a single sentence: `Cross-lens tension: career dominates over relationship (delta 0.7)`. There is no evidence drawer, no per-lens citation, no confidence band, and no reflection instruction. The LLM is asked to integrate this label into a chat answer with no scaffolding — the failure modes (parroting the label, inventing prose around it, generating dialectic content that ignores the chart) are the same failure modes that the existing Mirror prompt is already struggling to avoid.

The architecture would need to be rebuilt to honestly do what its name promises before exposing it to users. See §7 for evidence + remediation map.

> 1. Systems A and B use **incompatible domain vocabularies.** "Push vs Hold" cannot collide with "career-relationship pull" — they describe different axes. ## 7. Ungating recommendation: **Option C — REQUIRES REDESIGN**

### Evidence summary

1. **Mis-named surface.** `CROSS_LENS_PROMPT_SURFACE` does not gate cross-lens contradictions. It gates intent-domain contradictions. The actual cross-lens engine (System B) is already user-facing through the Today card. Ungating this flag would surface the wrong system under the wrong name.
2. **System A precision/recall is unfit for user-facing reflection.** 60% precision, 25% recall, single false positive on a benign chart-fact question, and zero variance across the four reference users (because user identity is not an input).
3. **System B per-lens signals are pre-canned per type.** Every Manifestor / Generator / Projector / Reflector / Reflector gets the same "tension" before any chart data is consulted; same for every Enneagram type. The astrology branch in System B reads from a non-existent collection (`db.astrology_charts`) so astrology contribution is silently absent and replaced by template strings.
4. **Numerology and LoC have no contradiction extractor at all.** Two of the five lenses listed in the product brief are structurally invisible to the contradiction system.
5. **The injection format is a category label with no evidence scaffolding.** A single line "Cross-lens tension: career dominates over relationship (delta 0.7)" is appended to the system prompt with no instruction on how the LLM should integrate it, no citation, and no confidence band. The LLM will either ignore it or fabricate prose around it — neither outcome is what the surface promises.
6. **The two systems use incompatible ontologies.** System A's `career/relationship/health` polarity pairs and System B's `push_vs_hold/control_vs_flow` clusters cannot be reconciled without a redesign of the domain vocabulary.
7. **The brief's own example ("Astrology → freedom, HD → consistency") is not representable.** Neither `freedom` nor `consistency` exists as a domain or cluster member in either system. The contradiction system cannot detect the canonical example the product team imagines it can.

### Blockers — none of these are within scope of a flag flip

| # | Blocker | Files |
|---|---------|-------|
| B1 | System A does not consult any lens engine; rename or rewire so that "cross-lens" means cross-lens | `services/cross_lens_synthesis_v2.py`, `services/intent_router_v2.py`, `services/mirror_chat_phase4_enrichment.py:868-879` |
| B2 | System B HD/Enneagram extractors are hardcoded per type | `services/tension_engine.py:2113-2128, 2219-2228` |
| B3 | System B astrology extractor reads from non-existent collection | `services/tension_engine.py:2044` (`db.astrology_charts` → should be `db.charts`) |
| B4 | Numerology and LoC have no extractors in System B | new files needed |
| B5 | Domain ontology mismatch between A and B | both systems |
| B6 | Injection block has no evidence drawer / no confidence band / no reflection instruction | `mirror_chat_phase4_enrichment.py:868-879` |
| B7 | `lens_coverage` is decorative — replace with actual lens-engine participation flags | `cross_lens_synthesis_v2.py:111-123` |
| B8 | No false-positive guard (e.g. "do not surface if the user's message is a chart-fact question") | new logic |
| B9 | No "complementary tension" vs "true contradiction" classifier — both surface as the same label | `cross_lens_synthesis_v2.py` |
| B10 | Brief's canonical example (`freedom` vs `consistency`) not representable; vocabulary gap | both systems |

### If Option B were chosen instead (NOT RECOMMENDED), the minimum-viable blocker set would be

1. **Rename** `CROSS_LENS_PROMPT_SURFACE` to `INTENT_DOMAIN_POLARITY_SURFACE` to match what it actually does, so engineering and product can stop confusing this flag with cross-lens contradiction.
2. **Add an evidence drawer** to the injected block: cite the 1-2 matched phrases (already available in `intent_envelope.evidence.matched_phrases`) and a soft confidence label, e.g. "saw both `career` and `wife` in your message — not a verdict, just a noticing".
3. **Add a chart-fact-query suppression**: do not emit if `forum_chat_knowledge_retrieval.classify_query(message)` returns `FACT_LOOKUP` or similar — these are not multi-domain reflection moments.
4. **Add a confidence threshold** that rejects emissions when only one domain has phrase evidence (the current floors permit emissions when the second domain's score comes entirely from frame / role / history bias).

This still ships intent-domain polarities, not cross-lens contradictions. **It is not what the product brief describes.**

### Recommended path (Option C)

Stop treating "intent polarity" as "cross-lens contradiction." Rebuild as two separate, honestly-named surfaces:

1. **Intent Polarity** (existing System A, renamed, optionally surfaced with evidence drawer per Option B). This is a real signal about message phrasing — it just isn't cross-lens.
2. **Cross-Lens Tension** (new): a per-lens signal extractor that pulls actual structured trait fields from `astrology.angles`, `human_design.{type, authority, profile, channels}`, `enneagram.{type, wing, instinct}`, `numerology.{life_path, expression, soul_urge}`, and a future LoC band field; emits a tension only when two of these structured signals can be projected into a shared dimension (e.g. "novelty seeking" / "stability seeking") via a published ontology that includes the brief's canonical concepts (`freedom`, `independence`, `autonomy`, `exploration`, `novelty`, `stability`, `security`, `belonging`, `control`, `certainty`).

Until that second surface exists, the `CROSS_LENS_PROMPT_SURFACE` flag should stay OFF.
