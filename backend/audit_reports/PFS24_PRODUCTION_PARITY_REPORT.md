## 3. Validation Questions — Answers

### 3.1 Did the correct role resolve?

**Spouse — YES.** Both Mel receipts:
- `resolved_role = "spouse"`
- `topology_role_type = "spouse"`
- `topology_confidence = "high"`
- `topology_inferred = false`

**Other categories — UNKNOWN.** No production traces visible from here.

### 3.2 Did the role land in the expected bucket?

**Spouse — YES.** `resolved_bucket="spouse"`, `framing_hint="couple_dynamic"`, `domain_bias="relationship"`. Exactly matches the PFS-2.3 spec.

**Other categories — UNKNOWN.** No production traces visible from here. Programmatic probes already demonstrated all 20 buckets in `PFS23_SHADOW_PROBES.md`.

### 3.3 Did `domain_bias` match the real relationship context?

**Spouse — YES.** `domain_bias="relationship"` correctly identifies the relational axis. The intent envelope's `lens_priority_after` confirms `relationship` is the dominant lens.

### 3.4 Did lens ordering improve after topology re-plan?

**Mostly NO — but for a correct reason.** Both Mel receipts show
`lens_priority_before == lens_priority_after`:

```
[relationship, astrology, human_design, enneagram, timeline, numerology]
```

This is the *post*-plan order. The intent envelope's V2 router already
ranked `relationship` at index 0 for these messages (because the
message itself was relationship-coded — "How does Mel map to me?" /
"My wife and I had a hard conversation"). The spouse bucket's
modulation (`relationship +0.40, astrology +0.30, human_design +0.20,
timeline +0.10`) cannot improve on a lens that's already top-ranked.

**But the orchestration plan itself changed:**
- pre-topology bucket = `self`, framing = `self_inquiry`,
  domain_bias = `self`
- post-topology bucket = `spouse`, framing = `couple_dynamic`,
  domain_bias = `relationship`

So the dashboard signals (bucket / framing / domain_bias) flipped
correctly; the lens stack just happened to not need a reorder
because the V2 router already knew the message was relational.

### 3.5 Were there any unexpected self fallbacks?

**No unexpected ones.** Two categories of `self` were observed:

| Category | Count | Reason | Expected? |
|----------|-------|--------|-----------|
| `self:default` (no resolved target) | 5  | Messages didn't reference any person | ✅ Expected |
| `self:unknown_role_token:family` (Isaac/Thaddeus via family_forum fallback) | 1 | No `child` topology edge → PFS-1 heuristic returns role=`family`, which is not in the topology vocabulary | ✅ Expected (documented in PFS-2.3 §5) |

**No silent fallbacks** — every `self` receipt carries an explicit
applied-rule string explaining why.

### 3.6 Were there any `unknown_role_token` events?

**Yes — 1.** Isaac receipt #6 carries `self:unknown_role_token:family`.
This is the PFS-1 family-forum heuristic emitting `role="family"`, which
is *not* a topology role_type. The token surfaces the data gap so
production observers can see exactly which targets need explicit
edges. **This is a feature, not a bug** — it identifies precisely the
production data quality work needed before any ungating.

## 4. Production Parity Recommendation — Sections A, B, C

### A. Is production relationship graph parity sufficient for ungating?

> **CANNOT BE DETERMINED FROM THIS ENVIRONMENT.**

Justification:
- Preview holds 2 edges (both spouse) — a strict subset of any
  plausible production graph.
- Pulsifi Leadership and other production forums are absent locally.
- Receipt persistence in this DB does not reflect production traffic.

To answer this question, the observation window must be run against
**production** receipts. Two viable paths forward:

1. **Read-only production access for the agent** (preferred):
   provision a read-only Mongo URI for `mirror_chat_retrieval_receipts`
   and `forum_relationship_edges` so the same scan can be run.
2. **Operator-driven snapshot:** the operator manually exports the
   production aggregates (bucket distribution, topology_role_found
   distribution, top-30 unknown_role_token events) and pastes them
   here for analysis.

### C. Is `RELATIONSHIP_ORCHESTRATION_PROMPT` ready for Stage-1 activation?

> **NOT READY.**

Reasons:
1. **No production observation evidence exists from this agent.** Stage-1 rollout is decided on observed production receipts; we have none.
2. **Preview observation is insufficient by design** — the only observable bucket is `spouse`.
3. **The PFS-2.3 code is provably correct** (102/102 unit tests + end-to-end receipt persistence on Preview with Mel) but correctness ≠ readiness without production observation.

**Recommended sequencing — unchanged from PFS-2.3 close-out:**

1. (operator) Provide production read-only access OR an operator-curated production-stat snapshot.

4. Confirm `unknown_role_token` rate is low (< 5% of replanned receipts) — if higher, there is a production data quality gap that must be filled before ungating.
